# 第一周执行计划：安全、范围、数据与基线冻结

> 对应总计划：[VIDEO_RAG_MASTER_PLAN.md](./VIDEO_RAG_MASTER_PLAN.md)  
> 周目标：在开始视频功能编码前，得到一个安全、可复现、范围明确且具备合法数据入口的研发基线。  
> 完成定义：本文件末尾所有 P0 验收项通过。

## 1. 第一周必须取得的结果

第一周结束时，必须具备以下成果：

1. 所有已暴露上游密钥完成轮换，源码中不再包含真实密钥；
2. 代码进入 Git 版本管理，形成可复现的 `baseline-v6-audit` 标签或等价提交；
3. 当前系统在本机可以完成静态检查、索引加载和至少一条离线/在线 smoke；
4. 8 类产品范围冻结，并完成视频可得性、许可和实物可得性审计；
5. 视频数据目录、元数据 schema、标注规范和数据划分规则冻结；
6. 每位标注者完成同一批试标，并得到第一版一致性结果；
7. 选出进入第二周验证的 ASR、视频编码器和 VLM 候选，不要求第一周训练模型。

## 2. 人员角色

建议三人除标注外分别承担一个主角色：

- 人员 A：工程与安全负责人。负责 Git、环境、密钥、测试、数据目录和 API 基线；
- 人员 B：数据与版权负责人。负责公开视频清单、许可记录、产品覆盖和失效风险；
- 人员 C：标注与论文负责人。负责标注规范、试标、文献表、实验表格模板和论文骨架。

三人都要参加试标，避免标注规则只由一个人理解。

## 3. Day 1：安全治理与仓库基线

### 3.1 立即轮换密钥

必须轮换所有曾经出现在 `config_runtime.py`、提交包、聊天截图或日志中的上游凭据，包括：

- 主回答模型 API Key；
- Embedding API Key；
- Rerank API Key；
- 路由分类模型 API Key；
- `/chat` Bearer Token。

注意：仅从文件中删除旧密钥不够，旧密钥已经视为泄露，必须在服务商控制台禁用。

### 3.2 配置改造设计

第一周完成方案和最小改造：

- `config_runtime.py` 只保留非敏感默认值；
- 真实值只从环境变量读取；
- `.env` 加入 `.gitignore`；
- `.env.example` 只出现占位符；
- 日志不得打印 Key、Token、Authorization 或 Base64 视频/图片内容；
- 部署阶段预留 Docker Secret 或平台 Secret 接口。

### 3.3 初始化版本管理

如果上级目录没有需要保留的 Git 历史：

```text
初始化 Git
添加 .gitignore
排除 .env、日志、缓存、模型权重、视频原文件和临时索引
提交清理前审计记录
提交安全基线
创建 baseline-v6-audit 标签
```

不得把旧密钥提交进新的 Git 历史。

### 3.4 清理交付问题

- 删除 `.DS_Store`；
- 处理 `run_api.sh`、`smoke_test.sh` 执行权限；
- 修复或隔离乱码 caption；
- 核对 README 中的模型名和超时配置；
- 记录 Windows 与 Linux 启动差异。

### Day 1 交付物

- `security_rotation_record.md`，只记录密钥名称、轮换时间和负责人，不记录值；
- `.gitignore`；
- 脱敏后的配置；
- Git 基线提交；
- 静态检查结果。

## 4. Day 2：复现当前系统与建立真实基线

### 4.1 环境锁定

记录：

- Python、CUDA、驱动和 PyTorch 版本；
- 两张 4090 的显存和设备编号；
- 实际安装依赖版本；
- Embedding、Rerank、LLM 的服务来源和模型版本；
- FAISS 索引对应的 embedding 模型、维度和构建日期。

建议生成锁定依赖，但不要在未验证前覆盖现有 `requirements.txt`。

### 4.2 基线运行

至少验证：

1. `validate_delivery.py`；
2. 检索索引加载；
3. 1 条客服问题；
4. 2 条技术问题，其中一条带图片；
5. 同一 session 的两轮追问；
6. 记录 P50/P95 不现实的话，先记录每条端到端耗时和各阶段耗时。

### 4.3 建立论文可用的基线报告

不得直接把现有 400 题准确率作为论文测试结果。第一周只记录：

- 当前数据和索引规模；
- 当前模块和模型；
- 已知公开题调优事实；
- 当前格式验证结果；
- 当前延迟与失败案例；
- 后续独立测试集的必要性。

### Day 2 交付物

- `environment_baseline.md`；
- `baseline_metrics.json`；
- `baseline_failures.md`；
- 一份可重复的启动和 smoke 命令清单。

## 5. Day 3：冻结产品范围与视频来源策略

### 5.1 对 8 类产品逐一审计

每个产品至少搜索 20 条候选视频，记录：

- 视频标题、URL、频道和语言；
- 时长；
- 是否有语音、字幕和清晰操作画面；
- 是否与现有手册的产品/功能相符；
- 是否包含完整步骤；
- 许可或允许的研究使用方式；
- 是否可以只发布 URL/ID 和时间戳标注；
- 视频失效风险；
- 是否能获得实物用于自录测试。

### 5.2 产品保留条件

一个产品进入第一阶段，应至少满足：

- 15 条以上可用公开视频；
- 覆盖不少于 3 个 procedure；
- 至少能定义正常操作、维护或排障中的两类任务；
- 许可策略可解释；
- 能找到或录制独立测试视频。

若不满足，先缩减产品数量，不用低质量或版权不清的视频凑数。

### 5.3 冻结数据发布策略

公开视频默认只发布：

- video ID/URL；
- 来源、许可和获取日期；
- 时间段和标注；
- 下载脚本；
- 文件哈希仅用于本地复现。

未经许可不发布原视频或重新编码副本。

### Day 3 交付物

- `video_source_inventory.csv`；
- `license_audit.csv`；
- `product_scope_decision.md`；
- 自录设备/产品获取清单。

## 6. Day 4：数据 schema、标注规范与试标

### 6.1 确定目录

建议先确定而不立即存入大量视频：

```text
data_video/
  manifests/
  annotations/
  raw/              # 不进入 Git
  processed/        # 不进入 Git
  keyframes/        # 大文件不进入 Git
  transcripts/
  indexes/
  splits/
```

### 6.2 冻结标注 schema

必须包含总计划定义的字段，并增加：

- `annotator_id`；
- `annotation_version`；
- `source_license`；
- `review_status`；
- `confidence`；
- `adjudication_note`。

### 6.3 编写边界规则

明确：

- 一个动作何时开始、何时结束；
- 语音先于动作时如何处理；
- 同一步骤被镜头剪辑打断时如何标注；
- 多个步骤重叠时如何处理；
- 仅展示部件、没有动作时属于什么类别；
- 错误动作和危险动作如何区分；
- 无法判断时必须使用 `unknown`，不得猜测。

### 6.4 三人试标

从至少 4 类产品各取 2 个视频片段，共 8–12 个样本，三人独立标注。之后比较：

- 产品和步骤标签一致性；
- 起止时间差异；
- error type 一致性；
- 手册章节对齐一致性；
- 分歧原因。

不要追求第一轮高一致性；第一轮的目标是暴露规范歧义。

### Day 4 交付物

- `annotation_schema.json`；
- `ANNOTATION_GUIDE.md`；
- `pilot_annotations/`；
- `pilot_agreement_report.md`。

## 7. Day 5：模型候选验证与第二周任务冻结

### 7.1 只做小规模技术验证

选择 3–5 条、总计不超过 30 分钟的视频，验证：

- FFmpeg/ffprobe 是否正常；
- 镜头切分速度和结果；
- Whisper 中文/英文 ASR 与时间戳；
- OCR 对按钮、型号和错误码的识别；
- 视频/VLM 是否能输出结构化动作和部件；
- 视频编码器能否在 24GB 显存运行；
- 单视频耗时、峰值显存和输出稳定性。

### 7.2 模型候选评分表

对每个候选记录：

- 模型版本和许可证；
- 显存；
- 处理速度；
- 中英文能力；
- 动作/部件识别；
- 时间定位；
- 是否支持批处理；
- 是否便于部署；
- 是否适合论文复现。

第一周不做大规模 LoRA，不构建完整视频索引，也不锁死单一模型。第二周根据实测结果确定。

### 7.3 周末评审

三人共同确认：

- 是否具备至少 5–8 类可行产品；
- 视频许可是否可接受；
- 是否能获得自录测试素材；
- 标注 schema 是否可执行；
- 模型能否在两张 4090 上运行；
- 第二周是否可以进入流水线开发。

### Day 5 交付物

- `model_candidate_matrix.csv`；
- `video_pipeline_pilot_report.md`；
- `week_01_review.md`；
- 第二周任务列表。

## 8. 第一周 P0 验收清单

- [ ] 所有曾暴露的密钥已在服务商侧禁用并重新生成；
- [ ] 源码、示例、日志和 Git 历史中没有真实密钥；
- [ ] Git 基线和版本标签已建立；
- [ ] 静态检查和基础 smoke 有可保存的结果；
- [ ] 8 类产品完成可得性、许可和实物审计；
- [ ] 至少 5 类产品满足保留条件；
- [ ] 数据目录、manifest 和 annotation schema 已冻结；
- [ ] 三人完成同批试标并处理主要分歧；
- [ ] 自录测试集的设备、场地、人员和授权方式已确定；
- [ ] 至少一个 ASR、一个 OCR、一个视频编码器和一个 VLM 在 4090 上跑通；
- [ ] 第二周开发任务已冻结。

若密钥、许可或独立测试数据三个条件中任一个不通过，第二周不得直接开始大规模数据下载或模型训练。

## 9. 第一周不要做的事情

- 不要一开始下载几百小时视频；
- 不要在未冻结 schema 前大量标注；
- 不要把公开视频原文件提交到 Git；
- 不要在旧公开 400 题上继续手工调规则并把结果当论文提升；
- 不要立即训练大模型；
- 不要把商业 API 的结果作为唯一论文基线；
- 不要在测试集冻结后根据测试答案修改阈值和 prompt。

## 10. 第一周完成后的决策

通过验收后，第二周开始实现：

1. 视频 manifest 和下载/登记工具；
2. FFmpeg 切分；
3. ASR、OCR、关键帧和结构化 caption 流水线；
4. 可缓存、可恢复、可追踪版本的视频预处理任务；
5. 小规模视频片段索引。

如果只有 5–6 类产品满足条件，则正式缩小范围，同时保持数据质量和独立测试，不延迟进入第二周。
