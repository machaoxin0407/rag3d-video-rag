# 验证报告

## 1. 验证目标

本报告面向 KBrag V6 初赛提交版，验证目标是确认系统满足以下要求：

1. 代码包完整，可安装依赖并启动 API；
2. 核心端点 `POST /chat` 可接收 JSON 文本和 Base64 图片字段；
3. `/chat` 返回统一 JSON 响应，具备鉴权、校验、超时和错误处理；
4. 产品技术问题可进入手册 RAG 链路，完成产品路由、检索、图文证据注入和答案格式化；
5. 客服问题与技术问题分轨处理，避免互相污染；
6. 代码注释覆盖率不低于初赛要求的 30%；
7. 公开题集离线验证和 A 榜结果证明方案具备有效性和稳定性。

## 5. 验证步骤

### 5.1 安装依赖

```bash
cd V6_submit_code
pip install -r requirements.txt
```

### 5.2 启动 API

```bash
./run_api.sh
```

如需指定端口：

```bash
HOST=127.0.0.1 PORT=8000 ./run_api.sh
```

### 5.3 健康检查

```bash
curl http://127.0.0.1:8000/health
```

预期响应：

```json
{
  "status": "ok",
  "engine_ready": true,
  "timeout_s": 50.0,
  "multimodal_timeout_s": 60.0,
  "auth_configured": true,
  "classifier_provider": "deepseek_binary_vote",
  "classifier_configured": true,
  "classifier_model": "deepseek-v4-flash"

```

### 5.4 `/chat` 文本接口验证

```bash
curl -sS -X POST http://127.0.0.1:8000/chat \
  -H "Authorization: Bearer $KAFU_API_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
    "question": "椅子的扶手使用一段时间后为什么会松动？",
    "session_id": "demo"
  }'
```

预期响应结构：

```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "answer": "...",
    "session_id": "demo",
    "timestamp": 1781320057
  }
}
```

### 5.5 `/chat` 图片字段验证

```bash
curl -sS -X POST http://127.0.0.1:8000/chat \
  -H "Authorization: Bearer $KAFU_API_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
    "question": "请结合图片判断这个部件应该如何安装？",
    "images": ["data:image/png;base64,iVBORw0KGgoAAAANSUhEUg..."],
    "session_id": "image-demo"
  }'
```

验证点：

- 合法 data URL 可通过请求校验；
- 非法图片格式、超出数量或大小限制时返回 422；
- 带图片请求使用多模态超时配置。

## 8. 关键专项验证

### 8.1 service / tech 路由

验证方式：

- 对公开题集进行 service / tech 标注对齐；
- 使用三路二分类 prompt 并行投票；
- 重复全量验证 5 次。

结果：

```text
5 次全量 400/400
```

结论：入口分类器 5 次全量测试准确率均为 100%（400/400），能够稳定区分客服问题和产品技术问题；API 层再用 `fake_qid=0/64` 复用 `agent.py` 的客服/技术 prompt 分支。

### 8.2 产品路由准确性

验证方式：

- `validate_performance.py` 读取 `data/product_mapping_final.csv`；
- 跳过 50 道 `非RAG` 客服题，只对 350 道技术题进行产品路由验证；
- 将人工产品标签归一化到 `data/catalog.json` 中的产品名；
- 调用当前 `ProductRouter.route(question, top_n=3)`，统计 Top-1 与 Top-3 命中；
- 读取 `submissions/v6_full_reference.csv`，复核最终提交答案实际引用或回答的产品归属；
- 生成 `validation_outputs/product_router_summary.csv` 和 `validation_outputs/product_router_details.csv`。

验证结果：产品路由 Top-1 命中 343/350，Top-3 命中 347/350；最终答案产品命中 348/350，未命中题为 432、433。无候选路由 0/350，产品标签归一化失败 0/400。结论：产品路由可稳定收窄技术题检索范围；少量路由误差可由后续 `search_manual`、hybrid retrieval、rerank 和 parent section 证据链路继续纠偏，例如 244 路由候选未覆盖 Boat，但最终答案来自 Boat 手册并回答正确。

### 8.3 多模态图文一致性

验证方式：

- `validate_performance.py` 解析 `submissions/v6_full_reference.csv` 的 `ret` 字段；
- 逐行统计 `<PIC>` 数量和末尾图片数组数量是否一致；
- 检查图片文件是否存在于 `手册/插图/`；
- 检查图片是否有 `data/image_captions_v4_final.json` caption 覆盖。

验证结果：图片锚点与数组一致率 400/400；最终答案共引用图片 780 次，图片文件存在率 780/780，caption 覆盖率 779/780。结论：图文锚点闭环显著降低图片错配风险，caption 覆盖基本完整。

### 8.4 幻觉抑制

验证方式：

- 对比 prompt 收窄前后的答案长度和无关补充；
- 检查技术题是否基于最相关 parent section；
- 检查模型是否输出手册未覆盖的经验性建议或不存在的图号。

结论：V6 将主动补充约束为“同一最相关章节内的直接补充”，减少跨主题扩展，提升回答与手册证据的一致性。

### 8.5 稳定性

验证方式：

- 静态自检；
- smoke 接口调用；
- `validate_performance.py` 自动生成验证数据表；
- 离线跑批检查缺题、fallback、格式错误；
- 保留 raw/trace 用于研发期复盘。

结论：提交包具备可启动、可验证、可复查的工程稳定性；默认不保留大量临时 trace，保证交付目录干净。

## 10. 风险与边界

| 边界 | 说明 |
| --- | --- |
| 用户上传图片理解 | 接口支持 Base64 图片并可传入模型；稳定得分主要来自手册插图和 caption |
| 会话记忆 | 当前为进程内短历史，服务重启后清空 |
| 自主学习 | 不在线写回知识库；采用离线 trace 复盘、数据清理和索引重建 |
| 上游模型依赖 | 主回答、embedding、rerank 依赖配置的远程服务 |
| 高分 6 轮方案 | 历史 A 榜分高，但超时风险较大，不作为默认交付口径 |

## 11. 验证结论

KBrag V6 初赛提交版已完成 API、源码、运行数据、检索索引、手册知识库、验证脚本和交付文档整理。验证结果表明：

1. `POST /chat` 满足初赛核心接口要求；
2. 源码包具备可安装、可启动、可自检的复现条件；
3. `validate_performance.py` 可生成验证报告所需数据表，覆盖 RAG 检索、图文一致性、路由准确性和对话连贯性；
4. 注释覆盖率达到 47.3%，超过初赛要求；
5. 技术链路具备产品路由、混合检索、图文锚点和幻觉抑制机制；
6. 公开题集与 A 榜验证证明方案有效，默认交付版选择稳定工程口径。

综上，本提交满足初赛对智能体 API、源码、技术文档和验证报告的核心要求。
